01The six buttons, answered first

Two different control groups were in the screenshot. Pause / Stop / Close are the flight page's header controls — they act on the whole flight. rerun / enhance / new are answers to one specific checkpoint (similarity-choice) — they decide what to do when your repos already have a feature.

ButtonWhat it doesWhere you landUndoable?

!
The one distinction that matters

Pause is a bookmark, Stop is a verdict, Close is just a door. Only Stop changes what the flight is (terminal, run killed, queue freed). Pause and Close both leave the work recoverable — Pause halts stage work resumable-in-place, Close doesn't even do that.

06Lifecycle controls — the full cluster

The header cluster is state-dependent but always present: Pause + Stop while the flight works, Continue + Start over when paused, Repeat a step + Start over + Delete when settled. Close is always there.

08Checkpoints — every pause, every option

A checkpoint parks its stage as waiting-for-approval (amber ?) — the flight status becomes needs approval, the pill gets the amber dot, a sticky toast fires. Answer via the option buttons on the stage (or MCP respond_flight_checkpoint — same endpoint). All are skipped by --yolo except missing-env (canary never guesses secrets).

similarity-choice: where rerun / enhance / new jump to

similarity.ts:47-100 → conductor.ts:746-775 (jump handling). Auto-answers: a confirmed plan-features split → new; --yolo → rerun.

!
Two different "rerun" buttons

similarity-choice → rerun re-points the flight at an existing feature and skips 7 stages. run-failed → rerun just starts a fresh test run inside the current flight. Same word, different scope — read the checkpoint label above the buttons.

Not a checkpoint but adjacent: plan-features is the pre-flight proposal flow (§04) — its confirm mints one flight per feature; the first runs, the rest queue.
